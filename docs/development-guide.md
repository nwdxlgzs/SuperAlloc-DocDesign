# 开发与设计推进指导

当前阶段只建设文档。此指导同时规定后续实现如何推进，但不意味着现在已经可以运行构建或测试。

## 1. 每次推进一个可检查的结果

1. 从 [TODO.md](../TODO.md) 选一个依赖已满足的任务。
2. 阅读该任务的 API 契约、不变量、平台边界和验收场景；先找已有决策，不重新猜测用户意图。
3. 文档任务先补输入、状态转换、成功/失败可见效果，再补数据结构和参数。
4. 与相邻子系统交叉审查，解决矛盾后再标记完成。
5. 后续代码任务先完成该阶段最小可验证实现，得到证据后再优化；更新待办及已知限制。

不要一次把“通用 allocator、持久事务、RT、所有平台、全部性能优化”作为无法独立验收的大任务。实施阶段在 PLAN 中有顺序，任务在 TODO 中有依赖。

## 2. 文档权威与修改规则

用户已确认要求 > PLAN 产品边界 > API 外部行为 > 子系统机制。发现这些层次矛盾时先修文档，不允许实现者任选一份。

字段/编号权威为[c-abi-spec](c-abi-spec.md)，默认公式权威为[configuration](configuration.md)，磁盘字节/提交恢复权威为[persistent-format](persistent-format.md)，跨操作资源和锁序权威为[operation-protocols](operation-protocols.md)。这些文档必须满足上层API而非覆盖它；不重复维护另一套字段表。平台实验概览与详细剧本通过ID对应，任务状态只在TODO勾选。

[状态机](state-machines.md)细化转换守卫、执行权及终态证据，[失败与恢复](failure-recovery.md)细化效果分类，[争用与吞吐](contention-throughput.md)细化维护调度与进展条件。它们与操作协议构成同一合同；不能把概念状态当成新公开health枚举，也不能只改流程箭头而漏改字段归属、配额和错误输出。

- 公共行为改动同步 API、ADR、TODO 和验证矩阵。
- 内部结构改动同步相关不变量、预算和基准配置；不影响契约时无需重新改变 API。
- 平台假设需要官方来源和实机验证任务；来源能证明 API 合同，不能替代本项目性能和资源测量。
- 所有“默认值”标注是设计基线还是实测调优值。实现不能随意把默认值变成硬编码上限。
- 新增文档链接必须能从导航抵达，不维护散落的第二套任务状态。
- 没有平台或测试结果时写“未执行/待验证”，不要把设计覆盖误写为测试通过。

## 3. 多 Agent 分工与集成

| 角色 | 主要负责 | 必须审查的相邻边界 |
| --- | --- | --- |
| 区间与自举 | architecture、arena-metadata | OS 事务、descriptor 生命周期、persistent/runtime ledger |
| 并发与性能 | concurrency、realtime、benchmarking | owner 移交、broker 锁边界、持久 free、资源统计 |
| 平台与存储 | platforms、persistence | Windows view/section、日志顺序、root、外部 map |
| 集成维护 | PLAN、TODO、API、验证、ADR、指导 | 名称、错误、生命周期和跨文档约束 |

同一时刻每份文档只有一个编辑者；审查者发出具体修改建议或切换编辑归属，避免相互覆盖。主集成者检查名称、模式矩阵、数值、状态机和待办证据一致性。

## 4. 后续实现约束

### 代码与接口

- 核心为 C++20；C ABI 头文件必须可被 C17 调用方编译。
- 核心关闭异常/RTTI，禁止默认 allocator 的 STL 动态容器和字符串，禁止全局初始化动态分配。
- 平台层、对象前端、broker、RT 和持久格式解析分模块，不让任一前端自行申请第二个不受管地址区间。
- 在实现前明确所有整数的单位与宽度，使用有检查的长度和 offset 运算；避免 packed 原子或未对齐控制字段。
- 首版原子只使用目标平台验证过的必要宽度。内存序必须附所有权/发布理由，不能用“全部 relaxed 更快”替代证明。
- OS error 和调用者可处理的 status 分离；错误报告不触发外部堆、日志 I/O 或递归回调。
- map/protect/flush/commit 不在 broker 热锁内执行；遵循架构文档的禁止嵌套约束。

### 内存与调试

- 每个 descriptor、索引节点、日志页、线程记录、RT 状态数组都计入预算。
- 记录逻辑 free 与物理回收的区别，空缓存不能同时记为 broker free。
- debug poison、guard、完整统计和 sanitizer annotation 是独立配置；默认性能报告明确是否启用。
- 不能用没有代价说明的 per-object header 或 cache-line padding 解决问题；先把 16B 对象和 16MiB arena 的开销算清楚。
- 严格 bootstrap 测试应拦截/计数被测模块外部堆调用；测试框架自己的内存要单独排除。

### 工具链与目录

后续创建构建系统时采用 CMake，区分核心、平台后端、测试、模型和基准目标；不在当前文档阶段创建空壳工程冒充实现。编译器矩阵至少包含 Windows MSVC/clang-cl、Linux GCC/Clang、macOS Apple Clang、Android NDK Clang，实际版本由 I-03 冻结并记录。

具体模块与命令目标见[构建规格](build-ci.md)，命令当前仅是未来约定；平台实验按[导航](platform-experiments.md)与[剧本](platform-validation.md)执行。接入例程依[集成指南](integration-guide.md)，资源和异常操作依[运行手册](operations-guide.md)，兼容冻结依[发布策略](release-policy.md)。

测试平台缺失时使用模型推进独立逻辑，但对应平台验收保持未完成。网络/CI 资源不足不得通过删除平台目标掩盖。

## 5. 审查问题清单

以下清单用于工程审查，不是每次要求用户批准的流程：

- 新范围由谁取得？旧 owner 何时失效？失败后谁仍持有它？
- 操作前是否预留了 split、rollback 和 quarantine 的元数据？
- 发布之后释放线程是否还接触可能被复用的对象或 descriptor？
- 元数据扩容是否递归进入普通 malloc，或在错误锁序下调用 OS？
- 未知持久提交会不会被当作失败无效果而提前复用？
- 32 位和 16KiB 页是否会改变原子、对齐、overflow 或磁盘几何？
- RT 路径是否新增了锁、CAS 循环、OS、动态分配、全池统计扫描？
- 睡眠 owner、线程退出、部分映射失败、只剩碎片时是否有明确结果？
- 一项优化的成本转移到了哪里：metadata、cache、RSS、commit、CPU 或尾延迟？
- 超时或后台观察是否误获执行权？已经发出的OS动作与还没取得阶段许可的动作能否区分？
- 某事务已确认成功、另一个事务触发WRITE_FAULTED时，返回值是否仍准确表达各自结果？
- 同一维护预算是否跨所有class/记录共用，游标是否前进，坏记录是否反复占住队头？
- 吞吐报告是否同时呈现到达率、完成率、拒绝率、积压及每线程进展，是否遗漏因系统变慢而未发出的请求？

## 6. 完成定义

文档任务完成需要：行为可判定、默认值与边界明确、失败路径完整、与其他文档无已知矛盾、链接有效、待实现项没有被误标完成。

实现任务完成还需要：适用测试通过、平台证据记录、错误与恢复路径验证、必要性能比较、ABI/格式兼容影响说明。设计文档存在、程序能编译或单一 happy-path 演示均不足以完成实现任务。

S-04/S-05的文档完成表示字段与流程候选可供实现和反证；ABI/正式store冻结另由I阶段门槛验证。不能用“依赖实测”留下整个文档未写，也不能用字段已写反推实测已经通过。收口通过[需求审计](completion-audit.md)逐项确认范围。

任务状态只在 TODO 勾选；证据引用与里程碑状态同步更新。项目当前没有运行时测试成绩，也没有性能排名。
